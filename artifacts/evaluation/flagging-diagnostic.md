# Production flagging calculation diagnostic

Date: 2026-10-31

## Scope and what was measurable

I traced the client evaluation/cache, Stockfish score normalization, move-feature extraction, flag calculation, server-side canonical recomputation, persistence, and flag display. I also ran the deterministic unit suites and added boundary/limitation checks.

The first read-only audit attempt could not reach the configured database. A later connection succeeded. After the shallow-flag backfill, the depth-stability diagnostic completed a full census of 64 persisted flags. See [flag-depth-stability.md](flag-depth-stability.md), the [full census CSV](flag-depth-stability-full.csv), and [diagnose-flag-depth-stability.ts](../../scripts/diagnose-flag-depth-stability.ts). These records still do not include independent human labels, so they cannot establish chess-mistake accuracy.

## Shallow-evaluation remediation

- The initial inventory had 36 of 81 persisted flags at actual depth 10 (30 high, 6 medium), despite their stored engine-version label. The other 45 flags were at depth 16.
- A widened dry run selected all 36 shallow-flag instances across 30 games, with no missing move/evaluation data. It considers the underlying plies of cascades as well as ordinary flags.
- At depth 16, 16 of the 36 original flags were re-emitted at the same flag identity, 9 had a corresponding loss below 100 cp, and 11 were not re-emitted as the same flag. By original severity: high 14 recovered, 8 fell below 100 cp, 8 no longer emitted; medium 2 recovered, 1 fell below 100 cp, 3 no longer emitted. “No longer emitted” can include recovery/causality or cascade regrouping; it is not assumed to mean a sub-100 cp loss.
- One high-flag game timed out on the first attempt, was explicitly reported, and succeeded on retry. Final retry dry run found zero remaining shallow-flag candidates and no unreachable games.
- Post-backfill inventory: 64/64 persisted flags have actual depth 16 (30 with the `target-v3` engine label, 34 with the prior `v2` label); none remain below depth 16.
- The depth-22 full census confirmed 55/64 flags (85.9%), downgraded 7, and reversed 2. For the 100-149 cp band, 6/9 remained at or above 100 cp (66.7%), 3 downgraded, and none reversed. This is evaluation stability, not human-label accuracy.
- The 150 cp+ thresholds and cascade/high rules were unchanged. The API suppresses any 100-149 cp persisted flag unless its actual saved point depth is at least 16.

There are no human-reviewed 'mistake / not a mistake' labels in the available repo data. Therefore precision, recall, and false-positive rate cannot honestly be calculated from the Stockfish evaluations or from persisted flags. Persisted flags are generated by the same rule, so matching them would prove reproducibility, not chess correctness.

## Production calculation path

1. Browser Stockfish evaluates the initial FEN and every post-move FEN once (`N + 1` searches for `N` moves) with Stockfish 19 lite at depth 16. Adjacent positions are reused.
2. Each `EvalPoint` stores before/after scores from the mover's perspective. After-position scores are sign-flipped from the next side-to-move perspective. The effective confidence depth is the shallower of the two searches.
3. The server validates the submitted score shape, per-ply indexes, depth >= 8, and move count; it reconstructs move features from the game's canonical stored moves and recomputes flags. Client-submitted flags are ignored.
4. A player move is eligible for an individual flag when its mover-relative `before - after` loss is >=100 cp and `checkCausality` finds no later position returning within 50 cp of the pre-move score.
5. Remaining qualifying runs can be summarized as a cascade: 2-4 consecutive moves by that player, each losing >=50 cp, total >=250 cp, full-confidence scores, and an unrecovered first move.
6. Severity is derived from evaluation loss only: 100-149 cp is low, 150-200 cp is medium; >200 cp is high. Low (100-149 cp) flags are suppressed below depth 16; cascade totals start at 250 cp, so cascades are always high.

## What passed

- `npm run test:flag-engine`: the flag-engine assertions passed, including White/Black perspective, severity boundaries, recovery at exactly 50 cp, depth confidence, mate transitions, incomplete sequences, timing behavior, and a cascade segmentation limitation.
- `npx tsx scripts/testEvalQuality.ts`: 21 assertions passed for normalization, mate sign/distance, sequence completeness, cache quality reporting, and N+1 evaluation reuse.
- `npm run test:sacrifice-detector`: passed. This tests a separate evaluation-backed sacrifice heuristic, not the production flag classifier.
- `npx tsc --noEmit`: passed.

These tests verify specified arithmetic and control flow on synthetic cases. They do not estimate real-game label accuracy or Stockfish stability.

## Calculation strengths

- Score perspective and sign conversion are covered for both colors.
- A move is not kept as a flag if a later evaluated position recovers to within 50 cp of its pre-move score.
- Incomplete per-ply evaluations are rejected by the flagger, and the server requires the submitted point count to match the canonical move count.
- Mate values are explicitly synthetic, marked `mate_only`, and the UI uses a forced-mate label instead of displaying them as ordinary pawn loss.
- The server reconstructs SAN/color/clock features from stored games, preventing client move metadata from being attached to another position.

## Field-by-field derived values

| Stored field | Current calculation |
|---|---|
| `cpLoss` | `Math.round(cpBefore - cpAfter)` in mover POV; mate scores map to signed (10,000 - mate distance). Individual moves must clear 100 cp. |
| `causality.heldToEnd` | Player-POV score after the candidate and every later ply is scanned; any later score >= pre-move baseline - 50 cp marks recovery. |
| `causality.worstFollowingCpLoss` | Stores the lowest later player-POV evaluation score (not a delta from baseline, despite the field name). |
| `timeSpentSec` | Feature extraction uses prior same-side clock + increment - current clock, clamped at zero; first own move uses initial time. Missing clock/increment context yields null, stored as 0 on a flag. |
| `clockRemainingSec` | Clock after the move, in seconds; missing data stored as 0. |
| `timeRatio` / `ratio` | Always 1.00 for both individual flags and cascades. |
| `phaseAvgSec` | Always 0. |
| `styleDeviationScore` | Always 0 for emitted flags. |
| `absoluteAnomalyScore` | `min(1, cpLoss / 500)`; cascades use total loss. |
| `severityBreakdown` | `{ evalLoss: rounded cpLoss, patternMatchBonus: 0, rushBonus: 0, tiltBonus: 0 }`. |
| `pivotMove` | Always null at flag creation; computed only later on demand by a separate UI action. |
| `cascadeMeta` | Only cascade flags: sequence length, first ply, and summed move-loss cp. |
| `gamePhase` | Set from post-move material <= 50% of starting material, or move number <=12; phase affects metadata, not eligibility. |
| `explanation` | Displays one decimal pawn loss or a mate-only warning; it is generated from the same flag classification, not an independent validation. |

Feature extraction also calculates capture/check/forcing, likely-premove, and snap-decision fields. The current flag selector uses only move color, ply, SAN/context, and the evaluation. Those tactical/time features do not influence its flag decision.

## Accuracy and product risks found

| Area | Finding | Effect |
|---|---|---|
| Human-label accuracy | No independent expert annotations are present. | Actual precision/recall is unknown; do not call 53%, 90%, etc. "flag accuracy." |
| Stockfish provenance | The authenticated client submits the evaluation numbers. The server validates score shape, finiteness, and minimum depth but cannot verify that Stockfish produced them. | A modified client can submit fabricated, finite scores and create plausible-looking flags for its own stored games. Server-side move canonicalization does not authenticate evaluations. |
| Search confidence | Depth 8-15 is accepted and marked `evalConfidence: degraded`; the UI displays a lower-depth caution. Depth 16+ is marked full. | Lower-depth 100-149 cp flags are suppressed at calculation and read time; flags at 150 cp or higher can still be emitted with the lower-depth caution. |
| Timing/profile factors | `flagMoves` explicitly ignores `profile` and `weaknessProfile`. All ordinary flags are `decision_error`; clock time does not gate or classify them. `timeRatio` is set to 1, `phaseAvgSec` to 0, and `styleDeviationScore` to 0. | Current flags are evaluation-loss flags, not time-pressure, recurring-weakness, or style-deviation detections. Move time is display context only. |
| Severity factors | The breakdown bonuses (`patternMatchBonus`, `rushBonus`, `tiltBonus`) are hardcoded to zero. | Severity currently means only the raw loss bucket; the advertised multi-factor formula is not active. |
| Cascade segmentation | A synthetic case confirms a recovered early loss can consume a later qualifying cascade run: the greedy scanner advances to the end of that run even when causality rejects its first move. | Can miss a cascade summary for later consecutive losses. The later single-move flag may still appear. This is a concrete false-negative path in cascade classification, though its production frequency is unmeasured. |
| Evaluation/cache quality | `inspectGameEval.structurallyComplete` checks ply coverage/uniqueness, but structural completeness is separate from score/depth validity. Cache retrieval gates on structural completeness; `resolveCpLoss` then skips unusable points. | Malformed score points can survive cache lookup and silently reduce flags rather than forcing reevaluation. Server push validation is stricter than the browser cache check. |
| CP scale | Mate-only changes use a synthetic 10,000 cp scale. | Correctly labeled as mate-only in the main card, but downstream numeric sorting/aggregates can mix synthetic mate scores with centipawn losses unless they filter confidence. |

## Bottom line

The arithmetic is deterministic and its core sign/threshold/recovery rules pass synthetic tests. The engine's output should be described as **"Stockfish evaluation losses that did not recover under this rule"**, not verified human mistakes. Real-world accuracy remains unmeasured. The most material correctness gaps are unverifiable client-supplied evaluations and the cascade false-negative path; the timing/profile/severity dimensions currently shown by the type system are not active in flag selection.
